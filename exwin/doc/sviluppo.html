Scrivere programmi

La catena e' chiusa: si compila dentro EX-OS

EX-OS ospita codice di terzi e lo fa girare da solo. GNU binutils 2.44 — as e ld — e' compilato per EX-OS: un programma assemblato e collegato qui e' identico byte per byte a uno prodotto dal cross-compilatore su Linux. E gcc gira dentro EX-OS, trova i propri header senza che nessuno glielo dica, e concatena da se' cc1, as, collect2 e ld fino a un eseguibile che parte. Lo stesso vale per g++, contenitori, std::string ed eccezioni compresi. 

    gcc -o prog prog.c
    g++ -o prog prog.cpp
    fbc  prog.bas                  FreeBASIC

Gli strumenti vengono dal CD tools, che e' un supporto a parte: si usano da li' (/cdrom/exos/bin/gcc) oppure si installano con install -tools.

Non copiare gcc in /bin. Calcola i propri percorsi da dove sta il suo binario: da /bin cercherebbe /libexec/gcc/... e risponderebbe cannot execute cc1, oppure che non trova stdio.h. Va lanciato da dove sta, o messo nel PATH con la sua bin.

make e i binutils

    make                make -j2                make -f altro.mk
    ar rcs libmia.a a.o b.o     ranlib libmia.a     nm libmia.a
    strip prog                  objdump -d prog

E' GNU make 4.2. Un esempio da provare sta in /cdrom/prova-make: si copia in una directory scrivibile (il CD non lo e'), si lancia make, e ./prova deve dire 385.

Meglio su ext2 che su FAT. Su FAT i nomi tornano in maiuscolo, e un makefile che nomina main.c non riconosce piu' il MAIN.C che gli arriva da un carattere jolly. make --output-sync non c'e' e lo dice invece di ignorarlo: vuole i lock di record di fcntl, che EX-OS non ha.

La libc

La libreria standard e' scritta qui: stringhe, memoria, stdio, printf e scanf completi di ampiezza e precisione, matematica, time, wchar. Gli header stanno in /exos/include sul CD degli strumenti.

Le funzioni POSIX rendono -1 e mettono errno. E' la convenzione che si aspetta chiunque abbia scritto C prima d'ora, ed e' quella che permette di ricompilare codice di terzi senza toccarlo.

Come e' fatto un programma

Un programma di EX-OS e' un ELF a 32 bit, ring3, collegato a 0x08000000. Il caricatore gli prepara i segmenti, uno stack con una riserva da 256 KB che cresce su richiesta, un blocco TLS se serve, e uno heap che comincia sopra l'ultimo segmento — con un tetto dichiarato e una pagina di guardia non mappata sotto il primo oggetto che c'e' davvero.

Le librerie condivise

Non c'e' ld.so, e non e' una mancanza da colmare: un linker dinamico vero e' mesi di lavoro, e ogni suo difetto sarebbe un difetto di tutte le applicazioni insieme. Qui una libreria e' un ELF normalissimo — non PIC — collegato a un indirizzo riservato nella fascia 0x04000000–0x08000000. Sta sempre li', quindi non c'e' niente da rilocare.

Cio' che serviva davvero — aggiornare una libreria senza ricompilare le applicazioni — si ottiene con la risoluzione per nome: la libreria esporta una tabella {nome, indirizzo} e l'applicazione chiede i nomi che le servono. Aggiungere funzioni, riordinarle, riscriverne il corpo: le applicazioni continuano a funzionare. Solo togliere un nome le rompe, esattamente come una DLL.

CosaCome sta in memoria
.text .rodata la stessa pagina fisica in ogni processo che la apre
.data .bss una copia fresca per processo, presa dall'originale

I dati scrivibili non si condividono, ed e' tutta la differenza. Condividerli vorrebbe dire che due applicazioni si scrivono addosso le variabili: la tabella delle finestre di ExWin e' in .bss, e sarebbe la stessa per tutti.

Un'applicazione grafica, dalla prima riga

#include "libc.h"
#include "exwin.h"

static long proc(ExFinestra f, unsigned int msg, unsigned int wp, long lp)
{
    switch (msg) {
    case EXM_CHIUDI:
        ex_esci(0);
        return 0;

    case EXM_COMANDO:
        if (wp == 1) ex_titolo(f, "hai scelto la voce di menu");
        return 0;

    case EXM_DISEGNA:
        ex_riempi(f, 0, 20, 300, 180, EX_GRIGIO);
        ex_scrivi(f, 12, 40, "Ciao da EX-OS", EX_NERO);
        ex_aggiorna(f);
        return 0;

    default:
        return ex_procedura_base(f, msg, wp, lp);
    }
}

int main(void)
{
    ExMsg      m;
    ExFinestra f, menu;

    f = ex_crea("finestra", "Esempio",
                EX_TITOLO | EX_BORDO | EX_CHIUDI,
                EX_AUTO, EX_AUTO, 300, 200, 0, 0, proc);
    if (!f) { printf("il server a finestre non risponde: avvialo con exwin\n");
              return 1; }

    menu = ex_menu(f);
    ex_menu_voce(menu, "File", "Prova", 1);

    while (ex_prendi_msg(&m)) ex_smista(&m);
    return 0;
}

exwin.h e il file da compilare insieme stanno in /exos/include sul CD degli strumenti, con anche exwin.bi per FreeBASIC e exwin.hpp per il C++.

La barra dei menu non restringe l'area del client. Il toolkit la mette in cima e larga quanto la finestra, ma il posto glielo deve lasciare chi scrive il programma: venti pixel. E' il motivo per cui l'esempio qui sopra comincia a disegnare da y = 20.

Per farla comparire nel menu di avvio basta una riga in /exwin/lib/applicazioni.txt — oppure la voce Applicazioni... del menu stesso. Vedi La scrivania.
